# T006 — Task 데이터 모델 설계

- **단계(phase)**: 데이터 모델 (data-model)
- **상태**: done
- **예상 소요**: 30분
- **선행 작업(dependencies)**:
- T005

## 설명

업무(Task) 테이블 스키마를 설계한다: 제목, 설명, 담당자, 상태, 우선순위, 시작/마감일, 예상소요시간, 완료보고서 등.

## 목표

대시보드와 보고서 기능에 필요한 모든 업무 필드를 스키마에 반영한다.

## 관련 요구사항 (개발요구사항문서.md)

> STEP 4 - 핵심 시나리오 2,3,4 / 비목표: 업무 상태별 우선순위·업무별 보고서 외 범위 제외

## 완료 조건 (Acceptance Criteria)

- [x] id, title, description, model, status, priority, startDate, dueDate, createdAt, updatedAt 필드가 정의됨 (담당자는 다대다라 `task_owners` 조인 테이블로, "보고서"는 `comments` 활동 이력으로 대체 — 메모 참고)
- [x] status/priority는 enum 또는 제약된 값으로 정의됨 (TS enum + DB CHECK 제약 둘 다, `drizzle/0003_task_check_constraints.sql`)

## 메모

- **assignee → task_owners 조인 테이블**: 디자인 검토(2a 위젯보드)에서 업무 하나에 담당자가 여러 명(예: "이준호, 정하늘") 붙는 경우가 실제로 있어서 단일 FK 대신 다대다 조인 테이블로 설계했다.
- **estimatedMinutes 필드는 만들지 않음**: 원래 이 AC에 있었는데, 개발요구사항문서.md 어디에도 "업무 예상 소요시간"을 사용자가 입력/조회한다는 요구사항이 없다. 우리 자체 개발 백로그(backlog.json)의 `estimated_minutes` 개념과 헷갈려서 잘못 넣은 것으로 판단해 제거했다. (T014 AC도 같이 수정)
- **"완료보고서(report)" → comments 테이블로 구현**: 별도 report 텍스트 필드 대신, 업무별 코멘트/활동 이력(`comments` 테이블)으로 "완료된 업무가 어떻게 진행됐는지"를 보여준다. 이미 사용자가 승인한 Claude Design "2a 위젯보드" 프로토타입(Artifact)이 이 방식으로 만들어져 있고, 요구사항문서의 실제 니즈("완료된 업무의 보고서를 보고 어떤 식으로 진행되었는지 알 수 있다")를 코멘트 이력이 그대로 충족한다.
