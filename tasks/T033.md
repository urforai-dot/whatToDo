# T033 — 달력을 간트 바 뷰로 재구현 (우선순위 색상/겹침 정렬)

- **단계(phase)**: misc
- **상태**: done
- **예상 소요**: 30분
- **선행 작업(dependencies)**:
- T031

## 설명

T031의 달력(하루 = 마감일 칩 하나)을 시작일~마감일을 잇는 바(Gantt 스타일)로 바꾼다. 하루에 여러 업무가 겹치면 우선순위 높은 업무가 위쪽 줄(레인)에 오도록 정렬한다. (2026-09-17 사용자 지시)

## 목표

"어떤 업무가 며칠부터 며칠까지 진행되는지"를 달력에서 한눈에 보이게 한다.

## 관련 요구사항 (개발요구사항문서.md)

> STEP 4 - 핵심 시나리오 2 (업무 우선순위 및 담당자 업무 로드 확인) — v1 비목표 범위 밖이지만 사용자가 이번 세션에서 명시적으로 추가 요청함 (T031과 동일)

## 완료 조건 (Acceptance Criteria)

- [x] startDate~dueDate를 가진 업무가 그 기간 전체에 걸쳐 색이 채워진 바로 표시됨 (하나만 있으면 그 날짜 하루짜리 바)
- [x] 바가 주(week) 경계를 넘어가도 같은 줄(레인)을 유지함 — 달력 전체 보이는 기간(6주)에 대해 레인을 한 번에 배정하고, 매주 따로 다시 계산하지 않음
- [x] 같은 날짜에 여러 업무가 겹치면 우선순위(P1이 위) 순으로 레인이 배정됨
- [x] 레인 배정은 실제 날짜별 점유 여부를 확인함 — "마지막으로 끝난 날짜"만 보는 방식이 아니라, 그 레인의 해당 구간이 전부 비어있는지 확인 후 배정 (동시에 겹치지 않는 업무끼리는 같은 레인을 재사용)
- [x] 레인이 최대치(3개)를 넘는 구간이 있으면 그 업무는 안 보이고, 위젯 헤더에 "+N건 안 보임"으로 안내함
- [x] 마감 지난(overdue) 업무는 바 전체에 테두리(ring)로 강조됨 (하루짜리 칸마다 반복되는 게 아니라 바 하나에 하나)
- [x] 우선순위는 5단계 순차(sequential) 색상 램프로 표시함 (accent 색 하나의 투명도 단계 — P1~P5를 서로 다른 색상으로 나누는 categorical 팔레트가 아님. 우선순위는 서로 무관한 항목이 아니라 순서가 있는 심각도라서)
- [x] 바 클릭 시 기존 TaskDetailPanel이 열림(T031과 동일한 `onSelect` 패턴)
- [x] 브라우저 + 실 데이터로 검증: 렌더된 각 바의 `gridRow`/`gridColumn`을 JS로 직접 읽어서, 여러 주에 걸친 업무들이 전부 동일한 레인 번호를 유지하는지, 날짜 범위가 실제 시작일/마감일과 정확히 일치하는지 확인함

## 메모

- **우선순위 색은 `dataviz` 스킬 로드 후 결정함**: priority는 서로 다른 항목(카테고리)이 아니라 순서가 있는 심각도(sequential)라서, 스킬 가이드대로 "하나의 색조를 밝기/농도로 바꾸는 램프"를 썼다. 앱 테마에 이미 있는 `--accent`(#5980a6) 색 하나를 투명도만 90%→30%로 5단계 나눠서 씀(`PRIORITY_BAR_CLASS`). destructive(빨강)는 "마감 지남" 상태 전용으로 이미 이 앱 전체에서 쓰이고 있어서, 우선순위 색과 절대 안 겹치게 분리했다.
- **adversarial-reviewer가 첫 구현에서 찾은 진짜 버그 2개, 둘 다 고침** (자세한 내용은 커밋 히스토리/이 세션 기록 참고):
  1. 레인을 매주(week)마다 따로 다시 계산해서, 3주에 걸친 업무 하나가 1번 레인 → 3번 레인 → 1번 레인으로 화면에서 줄이 왔다갔다 하는 문제. → 보이는 달력 전체(6주치 날짜)를 하나의 타임라인으로 보고 레인을 한 번만 배정하도록 재작성(`assignLanes`).
  2. 레인이 비어있는데도 업무가 "안 보임" 처리되던 문제. 원래 코드가 "이 레인에 마지막으로 배정된 업무가 언제 끝나는지"만 기억해서, 예를 들어 레인0에 나중 주(週)의 업무를 먼저 넣어버리면 그보다 이른 주의 다른 업무가 레인0의 빈 칸에 들어갈 수 있는데도 거부당했다. 실제로 시드 데이터 기준 "양산 이관 문서 정리"가 9/1~9/5 구간에서 사라지고, "고객 요청 사양 반영"은 9월 전체에서 아예 안 보이는 등 실제 데이터가 눈에 띄게 틀리게 나왔었음. → 레인별로 실제 날짜 배열(`laneOccupied[lane][dayIndex]`)을 만들어서 구간이 진짜 비어있는지 확인하도록 고침.
  둘 다 수정 후 브라우저에서 `document.querySelectorAll('button[aria-label*="~"]')`로 모든 바의 `gridRow`를 직접 읽어 같은 업무는 항상 같은 레인인지, 날짜 범위가 정확한지 재검증함.
- **처음엔 "하루 칸마다 버튼 하나씩" 방식으로 짰다가 다시 고침**: 그러면 5일짜리 바도 라벨(제목)이 하루 칸 폭(~80px, 10px 폰트로 3~4글자)에만 들어가서 거의 안 읽혔고, 키보드/스크린리더로 같은 업무를 최대 7번 반복해서 만나는 문제도 있었음(adversarial-reviewer 지적). CSS Grid의 `grid-column: N / span M`으로 주(week)당 업무 바 하나가 실제로 차지하는 칸 수만큼 폭을 갖는 버튼 하나로 바꿔서, 라벨 가독성과 포커스 이동 둘 다 해결함 — 이 방식으로 바꾸면서 "마감 지난 업무 테두리가 칸마다 반복되던" 것도 자연히 바 하나에 테두리 하나로 고쳐짐.
